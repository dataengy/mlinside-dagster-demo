# Runbook трёх живых демо лекции про Dagster

Спецификация живого показа. Проект — этот репозиторий; дека —
`content/preza-dagster-v2-content.yml` в курсовом репозитории MLInside (v2.2.0).
Демо-слайды деки: `017-demo-1-quick-start`, `026-demo-2-dagster-dbt`, `042-demo-3-mlflow`;
их подстрочники содержат тот же сценарий сжато. Источник правды — этот документ.

**Главный принцип.** Не демонстрировать набор текста. Демонстрировать **изменение состояния
системы и семантику графа**. Весь код написан заранее; на камере меняются данные,
конфигурация и выборка для пересчёта — но не исходники.

**Демо не добавляют лекции времени.** Они заменяют слайдовое объяснение: слайды, чьё
содержание показывается вживую, перенесены в приложение деки как screenshot fallback
(A14–A16). Основная часть — 64 слайда, 89.1 мин.

## Demo project

Все три демо идут на **одном** проекте; граф прирастает от демо к демо, ничего не пересоздаётся.

```
dbt_demo/                    dbt на DuckDB
  models/sources/            источники; ключи совпадают с ингест-ассетами Dagster
  models/staging/            stg_orders, stg_items
  models/intermediate/       int_order_features
  models/marts/              feature_mart + тесты → asset checks
  target/manifest.json       СОБИРАЕТСЯ ЗАРАНЕЕ командой `just dbt-parse`
src/dagster_demo/
  defs/quickstart.py         DEMO 1
  defs/ingest.py             загрузка сырья в DuckDB
  defs/dbt_defs.py           @dbt_assets (команда `build`)
  defs/ml.py                 DEMO 3
  translator.py              DagsterDbtTranslator — живьём НЕ пишем
data/raw/*.csv               сырьё, лежит в репозитории
data/features.parquet        витрина для DEMO 1; `just swap-features` перегенерирует её
data/mlflow.db               локальный SQLite MLflow (не сервер)
```

### Границы

| Нельзя | Почему |
|---|---|
| внешний API | недоступен из аудитории/на записи, отвалится молча |
| облачный деплой | тот же риск плюс задержки |
| сеть | пакеты, манифесты, датасеты — всё локально |
| скачивание пакетов на камере | `uvx`/`pip` тянут минуты и печатают простыни |
| `docker build` | минуты ожидания без содержания |
| долгое обучение | обучение обязано укладываться в **секунды** |

Модель в демо — маленькая выборка и простой классификатор. Если обучение занимает больше
десяти секунд, демо разваливается: уменьшайте выборку, а не терпите паузу.

## Pre-flight за 10 минут до записи

```bash
just reset      # сброс к состоянию «до демо» + сборка manifest.json
just smoke      # прогон всего графа; обязан закончиться RUN_SUCCESS
just reset      # ещё раз — smoke оставляет граф материализованным
just dev        # → http://localhost:3111
just mlflow     # во втором терминале → http://localhost:5000
```

- [ ] `just smoke` прошёл зелёным, потом состояние сброшено обратно.
- [ ] `dbt_demo/target/manifest.json` свежий (его делает `just reset`).
- [ ] `dg dev` поднят ДО начала записи, вкладка открыта на Asset Graph.
- [ ] MLflow поднят, в эксперименте ровно один прогон.
- [ ] `just swap-features 42` проверен заранее — это шаг «поменяли upstream» в DEMO 1;
      после проверки вернуть исходную витрину командой `just seed`.
- [ ] Все посторонние вкладки закрыты; в Dagster не открыты Runs / Schedules / Sensors / Deployment.
- [ ] Терминал: крупный шрифт, короткий prompt, история очищена.
- [ ] DEMO 1 — граф не материализован (узлы серые). DEMO 2 и 3 — материализован один раз.

## DEMO 1 — Quick Start · слайд `017` · ~6 мин

Граф на экране: `feature_table → training_dataset → trained_model`.

**Состояние до:** проект создан, три ассета из шагов 1–3 лежат в `defs/ml.py`, `dg dev` запущен,
граф ни разу не материализован.

| # | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Показать терминал с `dg dev` и вкладку браузера | интерфейс отвечает, слева три имени ассетов |
| 2 | Открыть Asset Graph | три узла, две стрелки; сказать, что стрелки нигде не объявлялись |
| 3 | Клик по `training_dataset` | карточка: описание, upstream, история пустая |
| 4 | Materialize all | узлы зеленеют сверху вниз; события в журнале — по ассетам |
| 5 | Карточка `trained_model` → метаданные | `roc_auc`, `rows`, `features`; вкладка с графиком метрики |
| 6 | `just swap-features 42`, обновить граф | `feature_table` и всё ниже помечено устаревшим |
| 7 | `just swap-features` затем Materialize от `feature_table` вниз | пересчитались три узла |
| 8 | Materialize ровно одного узла `training_dataset_qs` | пересчитался ровно один узел |

**Осторожно:** руками печатаются только две команды `dg launch`; код меняется подменой файла.
Вкладки Runs / Schedules / Sensors / Deployment не открывать — расписания и деплой ещё не введены.

**Fallback:** приложение **A14** (слайды `919`–`923`) — материализация, asset graph, метаданные,
селективный пересчёт. По слайдам уходит примерно вдвое меньше времени.

**Takeaway:** мы не запускали задачи — мы просили объекты; порядок и объём работы вывел граф.

**Возврат:** слайд `018-shag-8-checks-i-lineage`, граф остаётся материализованным на экране.

## DEMO 2 — Dagster + dbt · слайд `026` · ~9 мин · главное демо лекции

Граф на экране: `sources → dbt staging → dbt intermediate → dbt feature mart → training_dataset → trained_model`.

**Состояние до:** synthetic-ассет `feature_table` удалён, `training_dataset` зависит от витрины из
dbt; `manifest.json` свежий; `DagsterDbtTranslator` написан и работает; граф материализован один раз.

| # | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Показать `DbtProject` + `@dbt_assets` | десять строк — больше для подключения ничего не нужно |
| 2 | Asset Graph | dbt-модели как отдельные узлы, а не один чёрный ящик |
| 3 | Открыть SQL витрины, показать `ref()`, вернуться в граф | то же ребро; одна зависимость, записанная один раз |
| 4 | Клик по узлу dbt-модели | карточка: SQL, описание из `schema.yml`, история |
| 5 | Вкладка проверок этой модели | `not_null` и `unique` приехали как asset checks |
| 6 | Сломать данные в источнике, материализовать ветку | проверка красная, ветка ниже не поехала, соседние живы |
| 7 | Вернуть данные, показать шов `feature mart → training_dataset` | ребро между двумя мирами, а не между расписаниями |
| 8 | Селективный пересчёт вниз от витрины | dbt и Python отработали одним запуском в правильном порядке |
| 9 | Показать готовый `DagsterDbtTranslator` | рассказать про имена, группы и ключи — **не редактировать** |

**Осторожно:** не запускать `dbt run` из второго терминала — DuckDB заблокирует файл и демо встанет.
Не показывать граф на сотню моделей. Не уходить в объяснение самого dbt.

**Fallback:** приложение **A15** (слайды `924`–`929`) — подключение одной командой, `@dbt_assets`
на Python, сквозной граф, сшивка ключей, тесты как проверки.

**Takeaway:** dbt-граф не оборачивается в задачу — он становится частью одного большого графа,
у которого можно спросить «что пересчитать».

**Возврат:** слайд `027-level-3-particii-i-versiya-modeli`, сквозной граф остаётся на экране.

## DEMO 3 — MLflow / MLOps · слайд `042` · ~6.5 мин

Граф на экране: `dbt feature mart → training_dataset → trained_model → evaluation → registered_model`.

**Состояние до:** граф демо 2 продолжен вправо; MLflow поднят локально с file store; один прогон
уже сделан вчерашней датой; гиперпараметр вынесен в одну строку конфигурации.

| # | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Запустить ветку обучения от `training_dataset` вниз | три узла зеленеют, обучение — секунды |
| 2 | Карточка `trained_model` → метаданные | `mlflow_run_id`, `model_uri`, метрика |
| 3 | Клик по `model_uri` | открывается тот самый run в MLflow, идентификатор совпадает |
| 4 | Карточка `registered_model` | `model_version`; версией владеет MLflow, Dagster хранит ссылку |
| 5 | Подняться по графу вверх до dbt-источников | происхождение читается без внешнего каталога |
| 6 | Изменить гиперпараметр, обновить граф | устарели три правых узла; витрина и `training_dataset` свежие |
| 7 | Пересчитать устаревшее | три узла, не шесть; в MLflow новый run рядом со старым |
| 8 | Сравнить два run по метрике, вернуться в Dagster | «на каких данных обучена версия» — клик вверх по графу |

**Осторожно:** на экране ровно два run. Не переобучать «по-настоящему». Не обещать автоматической
выкатки — промоушен разбирается паттерном 4 дальше по лекции.

**Fallback:** приложение **A16** (слайды `930`–`936`) — MLflow в метаданных ассета, разделение
ответственности, вопрос «какая версия на каких данных».

**Takeaway (главный вывод всей практической части):**
**Изменение upstream или кода само определяет область lifecycle, которую действительно надо пересчитать.**

**Возврат:** слайд `043-patterny-pereobucheniya`; продолжаем с того, что пересчёт мы пока
запускали руками.

## Airflow: почему живого демо нет

Поднимать Airflow 2 и Airflow 3 ради одного экрана — плохой обмен времени на пользу: много
инфраструктуры, мало обучающего эффекта. Вместо демо — слайд `049-odin-pajplajn-tri-interfeysa`
с **одним склеенным кадром 3:1** из скриншотов **одного и того же логического пайплайна**
в Airflow 2, Airflow 3 и Dagster.

Требования к кадрам:

- один и тот же логический пайплайн: загрузка → преобразования → обучение → оценка → регистрация;
- одинаковый масштаб и одинаковая ширина окна у всех трёх;
- под каждым кадром одна подпись: система и единица графа;
- не подкрашивать левый кадр красным, а правый зелёным — слайд сравнивает модели, а не назначает победителя.

Пока кадра нет, слайд работает на диаграмме и подстрочнике; слот заведён как `wanted`
в `content/preza-dagster-v2-images.yml`, в подвале слайда стоит жёлтая 🔍-ссылка.
